# Трансформация

## Точки трансформации

Все три интервью из прошлого задания независимо указывают на схожий приоритет — **не трогать сразу ядро checkout / маршрутизацию**, а сначала навести порядок в данных и событиях:

### 1. Единый канонический слой бизнес-событий заказа и доставки
**Проблема**
Текущее представление создает конфликты с бизнесом: представления бинес-событий могут трактоваться неоднозначно.
**Бизнес-эффект**
Разные отделы (маркетинг, финансы, операционный блок) называют разные цифры по выручке кампании.
**Точка трансформации**
Договориться о единой модели бизнес-событий
**Метрика**
Не возникает ситуаций, когда разные отделы в отчетах указывают разные показатели.

### 2. Убрать обмен через БД
**Проблема**
Общая база перегружает создание заказа
**Бизнес-эффект**
Клиент долго ждет подтверждения, что заказ создан
**Точка трансформации**
Оставить синхронным только процесс создания заказа. Взаимодействи со службами доставки сделать асинхронным через брокер сообщений
**Метрика**
P95 времени создания заказа

### 3. Переработать статусную модель заказов
**Проблема**
Пользователи не понимают, в каком статусе находится их заказ. Командам поддержки не хватает инструментов диагностики по статусам заказов.
**Бизнес-эффект**
Пользователи очень часто обращаются в поддержку. Команды поддержки тратят много времени на ручной разбор, отвлекают разработчиков вопросами;
**Точка трансформации**
Ввести понятную статусную модель для поддержки с переходами по неуспешным веткам. Из этой статусной модели построить отображение в статусную модель для пользователей.
**Метрики**
Количество обращений в поддержку. Время разбора одного обращения командой поддержки

### 4. Снять тяжёлые аналитические выгрузки с операционной Oracle
**Проблема**
В пиковые нагрузки аналитические запросы сказыватся на производительности БД.
**Бизнес-эффект**
Пользователи дольше ждут подтверджение создания заказа
**Точка трансформации**
Асинхронно переливать данные из БД Oracle в отдельную БД для аналитиков (например, в Clickhouse)
**Метрика**
P95 времени ответа создания заказа в момент запуска аналитических отчетов

### 5. **Вынос промо-логики, чтения статусов, выбора маршрута**
**Проблема**
Ядро перегружено логикой и нагрузкой. Высокая связность компонентов внутри ядра.
**Бизнес-эффект**
Проблемы в одной части системы (баг в релизе, повышенная нагрузка и тд) влияет на все остальные части
**Точка трансформации**
Вынести промо-логику, чтение статусов, выбор маршрута
**Метрика**
Стабильность сервисов

## Целевая картина

1. У заказов есть понятные статусы для пользователей и поддержки. Пользователи меньше обращаются в поддержку за уточнением статусов, поддержка реже ходит к разработчикам.
2. Все сервисы обмениваются бизнес-событиями с единым конрактом, у аналитиков не возникает расхождений.
3. Тяжелые аналитические выгрузки выполняются в отдельной БД (например, Clickhouse). 
4. Заказ синхронно доходит до состояния создан. Остальной флоу выполняется асинхронно.
5. Проблемы в сервисах, не влияющих на критический путь создания заказа, не сказываются на создании заказа.
