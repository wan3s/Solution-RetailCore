# cutover-plan.md — переключение аналитической отчётности с Oracle на Clickhouse

> Связан с: `migration-roadmap.md`, этап 1 («Пилотный контур»). Раскрывает переход, обозначенный в разделе 10 roadmap.

## 1. Цель переключения

Перевести чтение самых тяжёлых аналитических отчётов и витрин (в первую очередь — отчёт по выручке кампаний и операционный отчёт по воронке заказов, которые сегодня дают разные цифры у маркетинга, финансов и операций) с прямых запросов к операционной Oracle на отдельную аналитическую БД (Clickhouse), наполняемую через канонический поток бизнес-событий (outbox/CDC), построенный на этапе 1.

Переключение решает две проблемы одновременно:
- убирает тяжёлую аналитическую нагрузку с операционной Oracle в пиковые окна (сегодня она влияет на P95 создания заказа);
- даёт единый источник для расчёта выручки/воронки, снимая расхождение цифр между отделами — это самый чувствительный для бизнеса риск (см. интервью с бизнес-заказчиком и с аналитиком).

Переключение **не меняет** сам расчёт цены, промо или статусов в монолите — только источник, из которого читается уже свершившийся факт для отчётности.

## 2. Объект переключения

| Параметр | Значение |
|---|---|
| Отчёты/витрины в scope | Отчёт «выручка по кампаниям» (маркетинг/финансы), отчёт «воронка заказов» (операционный блок) — как самые тяжёлые и самые конфликтные по цифрам |
| Отчёты вне scope | Всё остальное — переводится следующими волнами после подтверждения эквивалентности на пилоте |
| Источник до переключения | Прямые SQL-запросы к операционной Oracle + часть staging-выгрузок |
| Источник после переключения | Clickhouse, наполняемый из канонического потока событий (outbox/CDC из монолита, этап 1) |
| Период parallel run | Не менее 2 полных отчётных циклов (минимум 2 недели, включая один недельный пик продаж) |

## 3. Условия запуска (entry criteria)

Переключение нельзя начинать, если не выполнено:

- канонический контракт бизнес-события заказа согласован с аналитикой, логистикой и поддержкой (этап 0 roadmap) и стабильно работает без изменений схемы минимум 2 недели;
- outbox/CDC пайплайн работает в проде и не деградирует P95 создания заказа (проверено на этапе 1);
- в Clickhouse выполнен backfill исторических данных за согласованный период (минимум сопоставимый с периодом отчётности, на который ссылаются отчёты — как правило, 12 месяцев для отчёта по выручке);
- определены и согласованы с финансами и маркетингом контрольные метрики эквивалентности (какие именно цифры должны совпадать и с каким допуском);
- владельцы отчётов (финансы, маркетинг, операционный блок) проинформированы и подтвердили готовность участвовать в сверке;
- настроен дашборд сравнения Oracle vs Clickhouse по контрольным метрикам, доступный всем заинтересованным сторонам;
- есть согласованный владелец решения «продолжаем / откатываем» (go/no-go).

Если хотя бы одно условие не выполнено — переключение переносится, а не выполняется «по графику».

## 4. Роли и ответственность

| Роль | Ответственность на переходе |
|---|---|
| Архитектор (владелец roadmap) | Общая координация перехода, решение по эскалациям, финальный go/no-go совместно с бизнес-заказчиком |
| Разработчик аналитики (владелец пайплайна Clickhouse) | Backfill, настройка репликации, реализация сверки Oracle vs Clickhouse, технический go/no-go по качеству данных |
| Техлид монолита | Подтверждает, что outbox/CDC не влияет на транзакцию создания заказа и на производительность Oracle во время backfill и parallel run |
| DBA / владелец Oracle | Мониторинг нагрузки на операционную Oracle во время backfill и parallel run, право остановить backfill при риске для прода |
| Владелец отчёта «выручка по кампаниям» (финансы/маркетинг) | Подтверждает бизнес-эквивалентность цифр по выручке, участвует в приёмке, имеет право сказать «цифры не сходятся» |
| Владелец отчёта «воронка заказов» (операционный блок) | Подтверждает бизнес-эквивалентность операционных цифр |
| Бизнес-заказчик (Director of Digital Commerce) | Финальное подтверждение того, что расхождение цифр между отделами закрыто; владелец решения об откате при репутационном риске для отчётности |
| Дежурный/on-call инженер платформы | Мониторинг в день переключения и в течение окна наблюдения, первая реакция на алерты |

## 5. Состояние данных до переключения

Переключение источника отчётности — это в первую очередь вопрос доверия к данным, поэтому до дня Х отдельно проверяется:

- **Полнота backfill.** Количество строк/событий в Clickhouse за исторический период сверяется с количеством записей в Oracle с точностью до дня; расхождение объясняется (а не игнорируется), если оно есть.
- **Корректность трактовки бизнес-событий.** Отдельно проверяется, что отмены, возвраты и промо (главные источники сегодняшних расхождений, по словам аналитика) трактуются в Clickhouse так же, как согласовано в контракте события, а не повторяют произвольную логику старых пайплайнов.
- **Актуальность потока.** Задержка между записью в монолите и появлением события в Clickhouse (replication lag) измерена и держится в согласованных границах на пиковой нагрузке.
- **Отсутствие дублей.** Проверено, что at-least-once доставка событий не создаёт задвоения сумм в агрегатах Clickhouse (идемпотентность на стороне обработки событий).
- **Lineage контрольных метрик.** Для каждой цифры в пилотных отчётах зафиксировано и задокументировано, из какого события/поля канонической модели она считается — этого не было для старых пайплайнов, и это одно из явных требований к новому контуру.

## 6. Пошаговый сценарий

### T-14…T-7 (подготовка)

1. Заморозить изменения в определениях пилотных отчётов и в контракте события на время перехода.
2. Выполнить backfill исторических данных в Clickhouse, под контролем DBA по нагрузке на Oracle.
3. Настроить и включить дашборд сверки Oracle vs Clickhouse по контрольным метрикам (выручка по дням/кампаниям, число заказов по стадиям воронки).
4. Прогнать сверку на исторических данных, зафиксировать базовое расхождение (если оно не нулевое — объяснить и согласовать допуск).

### T-7…T-1 (parallel run)

5. Запустить оба источника параллельно: действующие отчёты продолжают читаться из Oracle, копии тех же отчётов строятся из Clickhouse и сравниваются автоматически ежедневно.
6. Ежедневно публиковать результат сверки владельцам отчётов (финансы, маркетинг, операционный блок).
7. Фиксировать все расхождения и их причины в общем реестре; критичные расхождения (по выручке) эскалируются в тот же день, а не в конце периода.
8. Провести отдельную проверку в день пиковой нагрузки (если период parallel run захватывает пиковое окно) — подтвердить, что репликация не отстаёт и не деградирует под нагрузкой.

### T0 (go/no-go и переключение)

9. Провести go/no-go встречу с участием архитектора, владельцев отчётов и бизнес-заказчика. Решение принимается по критериям из раздела 8.
10. При «go»: переключить конфигурацию пилотных отчётов на Clickhouse как основной источник. Oracle-источник не отключается, а переводится в режим «доступен для сверки и отката» минимум на 2 недели.
11. Уведомить владельцев отчётов и бизнес-заказчика о переключении и о том, куда смотреть в случае вопросов.

### T0…T+14 (окно наблюдения)

12. Ежедневная сверка Oracle vs Clickhouse продолжается в фоновом режиме (уже не блокирует использование отчётов, но остаётся сигналом раннего предупреждения).
13. Владельцы отчётов подтверждают на реальных рабочих циклах (закрытие недели/месяца), что цифры, которые они используют для решений, совпадают с ожиданиями.

### T+14…T+30 (закрытие перехода)

14. При отсутствии эскалаций и стабильной сверке — вывести из эксплуатации тяжёлые аналитические запросы к операционной Oracle для переведённых отчётов (снять нагрузку окончательно).
15. Зафиксировать переход как завершённый, обновить документацию lineage, взять пилотные отчёты как эталон для перевода следующей волны отчётов.

## 7. Наблюдаемость

Во время и после перехода отслеживаются:

| Метрика/сигнал | Что показывает | Где смотреть |
|---|---|---|
| Replication lag (outbox/CDC → Clickhouse) | Насколько отчёты в Clickhouse отстают от реальности | Дашборд платформенной команды |
| Расхождение Oracle vs Clickhouse по контрольным метрикам (выручка по дням/кампаниям, число заказов по стадиям) | Главный сигнал доверия к новому источнику | Дашборд сверки, доступный владельцам отчётов |
| Нагрузка на операционную Oracle во время backfill и parallel run | Не создаёт ли переход риск для checkout | Мониторинг DBA / P95 создания заказа |
| Ошибки/пропуски в обработке событий (dead-letter, повторные события) | Качество и полнота потока в Clickhouse | Логи пайплайна аналитики |
| Число обращений от владельцев отчётов с вопросом «цифры не сходятся» | Субъективный, но важный сигнал доверия бизнеса | Реестр эскалаций перехода |

Наблюдаемость сознательно строится так, чтобы расхождение было видно **до** того, как им начнёт пользоваться бизнес, а не постфактум — это прямой ответ на риск, названный самым чувствительным в интервью с бизнес-заказчиком и аналитиком.

## 8. Проверки после переключения (post-cutover validation)

Переход считается успешным, если в течение окна наблюдения (T0…T+14) одновременно верно:

- расхождение по контрольным метрикам (выручка по кампаниям, воронка заказов) между Oracle и Clickhouse ниже согласованного порога каждый день периода;
- владельцы отчётов (финансы, маркетинг, операционный блок) подтвердили как минимум на одном полном рабочем цикле (закрытие недели), что новые цифры пригодны для принятия решений;
- replication lag остаётся в согласованных границах, включая как минимум один пиковый период нагрузки;
- нет открытых эскалаций «цифры не сходятся» без объяснённой причины;
- P95 создания заказа не деградировал по сравнению с baseline (подтверждает, что снятие нагрузки с Oracle не создало побочных эффектов).

Результат проверки фиксируется письменно и подписывается архитектором, владельцами отчётов и бизнес-заказчиком — именно это подтверждение закрывает переход, а не сам факт технического переключения конфигурации.

## 9. Rollback-сценарий

### Условия отката

Откат инициируется, если выполняется любое из условий:

- расхождение по контрольным метрикам выше согласованного порога более одного дня подряд без объяснённой и согласованной причины;
- владелец отчёта (финансы/маркетинг/операционный блок) заявляет, что не доверяет цифрам из Clickhouse для принятия решений;
- replication lag растёт неограниченно или пайплайн теряет события без возможности быстро восстановить полноту;
- обнаружено, что backfill или продолжающаяся репликация ощутимо нагружают операционную Oracle и это влияет на P95 создания заказа.

### Шаги отката

1. Переключить конфигурацию пилотных отчётов обратно на Oracle как источник — это делается быстро, так как Oracle-путь не отключался, а оставался «в горячем резерве» минимум 2 недели после переключения.
2. Уведомить владельцев отчётов и бизнес-заказчика о причине отката и ожидаемом сроке повторной попытки.
3. Оставить CDC/Clickhouse-пайплайн включённым в фоновом режиме (не разбирать инфраструктуру) — он нужен для диагностики причины расхождения.
4. Провести разбор причины (root cause): ошибка в трактовке события, пропуски в потоке, неучтённый источник корректировок (например, ретроактивные изменения статусов, о которых говорил аналитик) и т.д.
5. Зафиксировать причину и исправление в контракте события или в пайплайне, повторно пройти parallel run для исправленного сценария перед повторной попыткой переключения.

### Владелец решения об откате

Решение об откате может инициировать любой из владельцев отчётов или DBA по своей зоне ответственности; финальное подтверждение — за архитектором и бизнес-заказчиком, если вопрос касается доверия к цифрам, используемым для бизнес-решений.

### Что не считается основанием для отката

Разовое, объяснённое и согласованное расхождение (например, из-за уже запланированной ретроактивной корректировки в Oracle, отражённой в Clickhouse с ожидаемой задержкой) не является основанием для отката — это фиксируется в реестре сверки как штатный случай.
